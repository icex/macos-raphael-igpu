# Candidate403: supported real-TSC mode, eight CPUs

Candidate400 booted eight CPUs in VirtTSCEmulated at4294967295Hz and panicked on non-monotonic scheduler time. Candidate401 retained that clock mode/frequency with one CPU, reached a software desktop, accepted keyboard input and continued to the238-second deadline without that panic. This supports an SMP contribution but does not prove a particular clock implementation defect. No physical GPU is used in these tests.

The pinned7.2.18 source already retained under run/c401-source provides a supported alternative. TMR3.cpp381–414 accepts the exact string RealTSCOffset;459–469 applies the4GHz clamp only to Dynamic or VirtTSCEmulated. With RealTSCOffset and no explicit TSCTicksPerSecond override, the guest should instead use the calibrated host frequency (~4699997773Hz). TMAllCpu.cpp495–523 reads SUPReadTsc for this mode, subtracts a vCPU offset, and retains the per-vCPU last-seen guard. The emulated guard's +64 increment is a plausible contributor to cross-CPU discrepancies, not established as the cause of400. RealTSCOffset is a diagnostic configuration, not a promised fix; it still requires observed mode/frequency and bounded native validation.

BootD uses eight CPUs, unchanged i7-6700K profile and the identical approved bootB loader. Only VBoxInternal/TM/TSCMode=RealTSCOffset is requested relative to400. The resulting frequency change is coupled to mode selection and will be reported explicitly; this is not a frequency-controlled comparison. No Dynamic setting, guessed clock frequency, kernel patch or firmware edit is added. Independent baseline VDI derivatives preserve all earlier disks. Preparation receipt: run/c398-vbox-clones/boot-d-preparation.json.

It does not force-unlock, alter old receipts, or treat other errors as success. Eleven focused tests cover success after temporary lock, changed-state refusal, other-error refusal and timeout.
