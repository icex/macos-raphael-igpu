## Constraints that every issue must satisfy

Candidate178-A and B use the same binary, configuration, probe and functional boot arguments. A recorded 483 and B recorded 531 failed final `AMDAccelMemoryMap::prepare` attempts. All 1,014 are classified `backing-pte`; capacity, VA/reclaim and unknown are zero. The retained samples in both runs are identical in the relevant fields: accelerator batch count 0, prepare count 0, flags `0xb13`, GPUVA `0x4000c0000` before and after false. `submitBuffer` is never called. Both probes return status 5 / `e00002bd` with zero completed work.

Three reviewed same-boot cleanup/reinitialization transitions—176→177, 177→178-A and 178-A→178-B—finish with authorizing schema-6 receipts and clean cursor-bounded host evidence. No host fault/reset is recorded. This leaves a causal hardware-lock claim unsupported, while it does not exclude every persistent hardware-state effect. The terminal ledger is 6/6; there is no authorized seventh launch.

The exact next method is X6000 `AMDAccelMemoryMap::commitIntoGPUPageTable` at file offset `0x3b4d2`, ABI `bool(map *)`. The safe 17-byte entry span is `554889e5415741564155415453504889fb`. The review-only candidate179 design proposes one observation here to distinguish rank 1 from rank 2 and capture raw branch inputs for ranks 3, 5, 9 and 10. Attribution must use a fixed-slot synchronous match on the same map pointer and kernel-thread token during one outer call; global counter deltas cannot correlate concurrent calls. No available slot, nesting, map/thread mismatch, unbalanced entry/exit, or unavailable conditional field is `unknown`, never `pre-commit`. The wrapper must preserve the native Boolean, call native exactly once, and must not call vtable slot `+0x168` again to observe its result. Raw fields remain unlabeled until constructors/callers prove their meaning. This design is not a hardware authorization.

The matrix has exactly 20 issues. Ranks 1–2 are the active sibling causes. Ranks 3–11 are conditional follow-ups that begin with offline source/ABI work. Ranks 12–20 remain downstream and untested while submission is zero.

## Four ordered stages

1. **Current backing/commit (ranks 1–11):** distinguish pre-commit backing from native commit rejection, then follow only the selected branch.
2. **Submission and client VM (ranks 12–15):** begin only after resource preparation/commit succeeds and a real submit occurs.
3. **Compute/render correctness (ranks 16–18):** begin only after queue consumption and completion can be observed.
4. **Presentation and lifecycle (ranks 19–20 plus the gate below):** compositor and output work begin only after verified offscreen rendering; every new exposure must independently satisfy the lifecycle gate.

**Lifecycle acceptance gate for every future hardware exposure:** exact immutable source/build/config/probe identity; explicit finite authority and unused ledger row; prior run-local and canonical schema-6 receipts semantically equal and independently valid; all queues retired and PSP commands confirmed; journal scan begins at the prior receipt's ending cursor and contains no host GPU/VFIO/IOMMU fault/reset; fresh capture/watchdog/sleep-inhibitor and VFIO/device/identity checks pass; no active VM, launch unit, pending reservation or sensitive process. Failure closes the proposed exposure. Passing this gate does not prove that no persistent hardware state exists; it makes the run comparable and keeps residual lifecycle state from being silently folded into a functional conclusion.

## Best elimination order

1. **Offline before another launch:** finish exact disassembly/caller proof for `0x3b4d2`, its two callbacks, raw field provenance, superclass call ordering, and safe object gates. This can refute bad instrumentation and reduce ranks 1–3, 5, 9 and 10 without touching hardware.
2. **One candidate diagnostic if reviewed and authorized later:** count commit entries/results while preserving the native return. Capture only already-read scalar fields. This single run selects rank 1 or rank 2 and may identify rank 3 directly.
3. **If no commit entry:** inspect the exact preceding backing/wiring call offline, then test ranks 4, 5, 6, 7, 8 and 11 only as the selected source branch demands. Do not alter page tables.
4. **If commit returns false:** follow only its selected callback. Resolve rank 3, then scratch allocation rank 9 and address/flags rank 10. Decode captured data offline before proposing one correction.
5. **If commit and map prepare succeed:** walk the client root and invalidation for rank 12, then observe publication rank 13.
6. **After actual submit:** evaluate queue consumption, IH/fence, shader and readback in ranks 14–17.
7. **After compute passes:** move to offscreen render rank 18, compositor rank 19, and the explicitly chosen display transport rank 20.

This ordering does not assume one launch per row. Ranks 1–3 share one planned observation. Several rank-4–12 decisions are source/ABI/byte-decoding tasks. Ranks 13–20 should reuse evidence from the first workload that actually reaches them.

## Stop and keep-open thresholds

- **STOP hardware use** on any host fault/reset, guest panic, capture loss, terminal queue timeout, unretired work, or invalid recovery receipt. Preserve the run before interpretation.
- **STOP phase interpretation** if `unknown` is nonzero or lifetime counters overflow without a reliable total.
- **STOP broad memory mutation** until rank 1 versus rank 2 is measured. An assigned GPUVA is state evidence, not proof that backing or commit succeeded.
- **STOP firmware, shader, SDMA execution, IH and display mutation while submit is zero.** Their execution-time forms cannot cause a path never entered. Pre-submit capability values remain separately testable when a concrete backing field selects them.
- **STOP allocator changes based on GPUVA zero.** Flags bit `0x20` permits legal assigned zero; candidate178's observed GPUVA is nonzero in any case.
- **STOP adding launches after the terminal 6/6 ledger.** Further hardware work requires a separately reviewed policy; offline research can continue.
- **Keep ranks 1–11 open conditionally** until the exact native split is known.
- **Keep ranks 12–20 untested**, not ruled out, until their prerequisite path is reached.

## Offline conclusions already earned

These conclusions reduce the matrix without additional GPU exposure:

- Capacity-fast-fail and final-retry GPUVA allocation/reclaim are not the observed candidate178 cause: exact counters are 0 in both runs, assigned bit remains set, and GPUVA is stable.
- GC hardware IP version and LLVM compiler target suffix are different namespaces. Linux maps GC10.3.4 to `gfx1032` and GC10.3.6 to `gfx1036`; the number 10.3.4 does not imply `gfx1034`.
- Linux deliberately shares GMC10, GFXHUB2.1 and the Navi10 PTE/PDE format across GC10.3.4 and 10.3.6, so a wholly unrelated page-table encoding is unlikely.
- Linux deliberately differs on policy: GC10.3.6 is APU, gets 1 GiB GART versus Navi23's 512 MiB default, gets zero versus 32 MiB MALL, and can prefer system GTT over carved-out VRAM. These are audit leads, not automatic Apple constants.
- Physical discovery supports one SDMA engine and the integrated 5.2.6 queue policy; recreating a fictitious second engine is not a valid repair.
- Native KIQ/engine success and clean recovery validate the tested lifecycle path. They do not prove a client resource map, user queue, IH completion, shader result or desktop presentation.
