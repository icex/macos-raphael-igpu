## Decision

Cleanup cannot proceed through an existing recovery path. Both the manifest-selected
`terminal-prefix-open` parser and `tools/recover-frozen-run.py::build_proof` refuse
the frozen transcript with `CriticalReplayError: CR2 snapshot has a missing chunk`.
Snapshot 2 is complete but is not terminal. Snapshot 3 has the terminal END and four
missing chunks, so there is no currently admissible final capture.

An additive one-run migration proof is feasible without changing or weakening the
five recovery helpers pinned by the candidate manifest. It must remain a new,
explicit candidate-183 wrapper, preserve the original transcript byte for byte, and
insert only the four independently integrity-validated donor chunks into an in-memory copy.
The unchanged terminal-prefix parser must then validate the entire augmented
transcript against snapshot 3's original END before unchanged schema-3 recovery may
be called. This design is evidence for independent review; it is not authorization to
execute recovery.

## Candidate-183-only migration proof

The preferred integration is a new standalone, one-run wrapper. Existing
`terminal-prefix` and `terminal-prefix-open` meanings and the five manifest-pinned
helpers remain byte-identical.

### Proof-only phase

1. Read the original manifest, serial, failed `recovery.json`, and `verdict.json`
   bytes and require the exact sizes, SHA-256 values, run, boot, build, CR2 schema,
   lease schema, and selector listed above. Require the manifest's five helper hashes
   to equal current file hashes. Pin the new wrapper and every additional executed
   source, including `tools/experiment.py`, separately; do not substitute those
   hashes into the manifest helper map.
2. Require the unchanged strict parser to refuse the original serial with its actual
   `CR2 has a malformed transport line` error. Require the manifest-selected
   unchanged tolerant parser to refuse it with the exact
   `CR2 snapshot has a missing chunk` error.
3. Decode transport with the same bounds, grammar, chunk checksum, monotonic snapshot,
   foreign-build, conflicting-chunk, and conflicting-END rules. Require snapshot 3
   to be the unique latest END and the final transport marker, with its exact END
   fields above and no later/open/foreign transport.
4. Integrity-check snapshot 2 with unchanged `_reconstruct`; require its exact END and
   267-record prefix. Require snapshot 3 to be missing exactly the four parts of
   record 134, with no valid target chunk at those keys. Obtain each payload only
   from the checksum-valid, fully reconstructed donor record. Refuse a donor or
   target mismatch, any other missing target chunk, any valid chunk beyond terminal
   count, or any conflict among all checksum-valid chunks retained by every earlier
   attempt.
5. Construct four target transport lines with snapshot number 3 and newly calculated
   per-chunk CRCs. Build the derived input by inserting only those four lines at the
   unique byte offset immediately before the original snapshot-3 END. Do not remove,
   replace, normalize, or reorder any original byte. Thus the original transcript is
   a byte-for-byte prefix/suffix composition of the derived input and all original
   malformed lines remain visible to the unchanged tolerant parser.
6. Pass that complete derived input through the unchanged terminal-prefix parser.
   Require it to select snapshot 3 and reproduce the original END's count, bytes,
   chunks, drop, truncation, CRC and FNV exactly; require exact snapshot-2 prefix
   equality. Also strict-parse a minimal diagnostic representation consisting of
   the reconstructed terminal chunks and original END, solely to demonstrate that
   the terminal record set is internally canonical. Scan the selected records and
   all valid later/direct protocol evidence for ABORT; require exactly matching
   OWNED, ACTIVE POOL and VALID lifetime identity for the manifest run.
7. Write one O_EXCL proof containing the original artifact hashes, original parse
   errors, all manifest identities and helper hashes, wrapper/additional-source
   hashes, donor and target raw END lines and line numbers, insertion byte offset,
   each donor line/chunk and derived line/chunk with hashes, the derived-input hash,
   reconstructed-record digest, and both unchanged-parser results. The proof is not
   a recovery receipt or launch authority.

Any identity, source, input, helper, donor, target, conflict, ABORT, loss counter,
terminal position, reconstruction, or digest discrepancy refuses without writing a
proof.

### Explicit one-use execution phase

After independent review of a concrete wrapper and proof, an explicit execution
mode would re-read every input and recompute the proof byte for byte. Before any
device access it must create an O_EXCL attempt marker bound to the proof hash; an
existing marker forbids retry even if a prior execution stopped before recording a
result. It then supplies the derived transcript only in memory to unchanged
`experiment.recover_v2`, with the original manifest and original five-helper map.

The unchanged recovery path continues to require the exact run-bound OWNED and
ACTIVE pool evidence, the first VALID lifetime read, and the second identical live
lifetime read immediately before the first scratch write. The migration wrapper
does not reconstruct, cache, or bypass those BAR observations.

After the call, the wrapper writes a separate O_EXCL migration result containing the
attempt and proof hashes, original and derived transcript hashes, the returned
receipt bytes/hash and recovery ID, or the exact failure. It must leave the original
serial, manifest, verdict, and failed run `recovery.json` unchanged. The canonical
schema-6 receipt created by unchanged VFIO recovery retains its existing identity
and helper fields; the separate result supplies reconstruction provenance.

Because the run's `recovery.json` remains the original failed result, existing warm
admission cannot silently equate it with a newly created canonical receipt. Any
future same-boot launch would need a separate reviewed authority that explicitly
validates the migration proof/result and their receipt hashes. Cleanup execution
alone does not grant that authority and has no automatic retry.

## Safe next step

The design is technically feasible without weakening the current parser or live
schema-3 recovery gates. The next step is offline implementation plus adversarial
tests, followed by independent review of the exact proof bytes and source hashes.
Until that review explicitly authorizes the one-use execution, the existing cleanup
gate remains closed. Reboot remains the only cleanup alternative that does not need
this migration path.
