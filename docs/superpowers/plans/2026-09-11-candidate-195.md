# Candidate 195 offline plan

## Goal
Use an observation-only candidate to distinguish VRAM backing allocation pressure, page-table commit, and queue retirement while preserving the demonstrated candidate-194 GPU path.

## Gates before hardware
1. Pin the exact clean source commit and source digest.
2. Extend the staging card contract and focused regression tests.
3. Build the kext, release bundle, debug symbols, and identity manifest from a clean worktree.
4. Run exact-KDK preflight and the full Python suite; resolve any recovery/VM safety failures without weakening gates.
5. Create fresh, candidate-specific staging and one-run authority from a verified prelaunch/refusal record; do not reuse candidate-194 reseal artifacts.
6. Before launch, verify current boot, sleep inhibitor, watchdog/pstore, amdgpu handoff, and cleanup authority.

## Hardware test
Run one bounded headless small-metal experiment only after all gates pass. Inspect raw serial before classification. Record allocation counters, map phase, VMID-2 walk, CP stall state, stamp completions, and recovery receipt.

## Decision
- Allocation failures with no corresponding map/PTE failure: investigate allocator capacity/fragmentation.
- Valid allocations and map/PTE but stamp timeout: investigate queue retirement/CP completion.
- Any regression in startup or cleanup: stop, archive evidence, and review before another cycle.
